# 错题记录与治理 SOP

## 1. 适用范围

当前工作区 内所有 Agent（包括 Hi 小跟班）记录本项目共享指令、SOP、Skill、桥接、自动化或治理流程中已核验的实际失败及疑似机制缺陷。错题本用于改进项目体系，不是所有业务的故障库。守墓人每轮新建独立 配置中已核实可用的模型 / xhigh 会话归因，本轮开发、测试和验收全部闭环后归档并保留历史；按影响优先级启动调研、定位、SOP 沉淀或独立开发，首次发生也可治理。守墓人不开发业务代码，负责调度、亲自测试、受控应用与最终验收；开发 Agent 只提交候选代码。

## 2. 执行前

- 先按运行时授权选择执行分支：有共享账本权限的本机执行者在 `<工作区绝对路径>` 使用 `.codex/gravekeeper/notebook.py`；隔离 Hi 成员只在运行时绑定的 `WORK_ROOT` 内记录。本文对全部隔离成员只读开放，文内路径和链接不增加权限。
- 治理与归档步骤仅由获授权的守墓人/项目维护者执行；详细职责见 [.codex/gravekeeper/守墓人.md](../.codex/gravekeeper/守墓人.md)。隔离成员仅执行下述记录与回执验收分支，不访问该职责文件、共享账本或治理配置，不启动其他 Agent。
- 只记录自己执行或可直接核验的事件；不读取其他成员会话，不写凭据、签名下载链接、完整业务数据或群聊原文。共享的是脱敏问题证据。
- 整个功能不扩大 Hi 群成员修改调度、桥接或通知配置的权限。错题本提交是自动记录的明确例外，不需要用户每次重新要求。
- 提交者核实失败事实和发生环节即可，根因允许待定位。记录部分失败、静默跳过、错误回执、降级及额外人工补救；即使已返回失败、已有绕行方案或任务最终完成，也应记录实际流程缺口。
- 成员身份、登录态、权限上下文识别失败属于应记录场景。写清已授权能力、实际错误和影响，不因错误包含“登录/权限”就直接排除，不复制凭据。
- 已确认纯业务数据、一次性脚本、正常需求或外部故障，且共享流程已正确识别、提示和处置的，留业务目录。无法确认是否机制缺陷但能核验共享环节失败，先提交 candidate 供守墓人调查；无失败事实的猜测不提交。
- 隔离 Hi 成员保持本人目录权限：按运行时提供的字段说明写入本人 `.notebook-outbox/<稳定事件名>.json`；可信桥接仅代收这些显式脱敏报告，写同名 `.receipt`。accepted=true 表示已收录候选；失败回执留本地修正，删除回执后在下一次任务重试。成员不能直接访问共享账本或其他成员目录。

## 3. 操作步骤

### 1）判定与记录

依次核实：① 哪个共享环节出现异常；② 预期与实际有何差异，证据在哪里；③ 影响谁、是否可绕行或需要人工补救。确认事实后记录，机制归属和根因由守墓人继续核实。

例如：成员在 Hi 发起已授权任务，但登录信息无法识别且仅收到失败回执，应记录为身份/登录识别环节的 candidate；不能未经调查写成“凭据失效”或“桥接 bug”。

隔离 Hi 成员将 UTF-8 JSON 保存至本人 `WORK_ROOT/.notebook-outbox/<稳定事件名>.json`，按运行时字段说明填写；`agent`、`session`、`business`、`incident_key` 由可信桥接绑定，成员无需编造。完成报告后由桥接在任务结束时代收，后续检查同名 `.json.receipt`；仅 `accepted=true` 才报告已收录候选。到此结束成员提交步骤，不执行下面的本机命令或治理操作。

有共享账本权限的本机执行者将 JSON 保存至本业务目录的临时文件，或通过 stdin 提交：

```bash
python3 .codex/gravekeeper/notebook.py submit < 本业务目录/错题提交.json
```

本机直接提交的必填字段如下；隔离成员除上述由桥接绑定的四项外，按同一内容要求及运行时说明填写：

| 字段 | 填写规则 |
| --- | --- |
| scope | 对象：domain 为 instructions/sop/skill/bridge/automation/governance；component 为具体共享环节/文件；observed_evidence 为已核验的失败事实（兼容旧 causal_evidence 字段）；reusable_reason 为同类影响。根因未知在 conclusion 标待定位 |
| incident_key | 稳定事件标识：如 hi:消息ID:故障环节、task:任务ID:故障环节。同一事件跨 Agent 转述沿用原标识，不带重试序号 |
| title | 最多100字，说明哪项操作出现什么问题 |
| agent / session | 记录者名称和真实 session ID；不可获得时明确写 unknown，不编造 |
| business | 业务目录或组件名称 |
| occurred_at | 实际发生时间，ISO8601 带时区；无法确认写 unknown 并增加 time_note 说明可确认范围/缺失原因，历史回扫不填提交时间 |
| trigger | 触发操作、必要输入和环境条件 |
| expected / actual | 预期行为、实际现象/关键错误码 |
| evidence | 1–12条证据字符串：项目内相对路径、命令结果摘要、可定位的时间/行号。不要只写“见日志” |
| attempts | 已尝试方案及结果；未尝试明确说明 |
| conclusion | 已确认根因或“待确认”与推断依据，分清事实与猜测 |
| impact | 阻塞、影响范围，以及是否已有临时办法 |

新记录进入 candidate（待范围复核），不能直接建专题。程序检查字段，语义和因果关系仍由守墓人核实；不得为通过校验虚构 scope。无数量目标，允许零新增。返回 duplicate=true 表示同事件已记录；用 `amend E-ID --note '新增证据与结果'` 补充，不增加次数。提交失败先纠正格式/脱敏；不阻断原业务回复，不谎报已记录。记录可在任务中发现问题时写入，也可完成/失败后补写，无需每次开工记流水。

### 2）分析与治理

- 守墓人先用 `show E-ID` 核实范围，再执行 `assess E-ID`，stdin JSON 示例：

```json
{"decision":"accepted","note":"核验到共享环节实际失败，具体根因待定位","scope":{"domain":"bridge","component":".codex/hi-bridge/bridge.py 的具体函数","observed_evidence":"填写实际核验结果，不照抄占位说明","reusable_reason":"说明同类群任务如何受影响"}}
```

已确认不符合范围且共享处理正常用 `{"decision":"excluded","note":"具体排除原因及所属业务目录"}`。只有守墓人/项目维护者维护范围状态，提交者不自行审核。旧记录也要复核；accepted 表示共享失败环节已核实，不要求代码根因已知；之后才能 group、评优先级或开发，单纯 review 不等于收录通过。
- 历史误收项标 excluded，保留原 ID、原文、专题关系和审计，可 search/show 查询；从活动索引与治理计数排除，不伪装成已修复。原专题无有效记录时移出活动专题。后续有新体系证据可对原 ID 再 assess accepted，不重复提交；普通 amend 不撤销排除。专题有未完成开发任务时禁止静默排除，先核实任务状态再处理。
- 提交增加 revision；每60秒检查，5分钟启动冷却，每轮通过 Herdr 新建独立 session，effort 固定 xhigh；仅在配置 governance_full_access=true 且所有者授权后，启动时显式传 `--dangerously-bypass-approvals-and-sandbox`（full access + never），跳过目录信任和命令审批，不改全局配置。首条任务执行 guardian-start 绑定 G-ID、准确 session UUID、终端和巡检快照；忙碌或审批阻塞时保留本轮。守墓人分析新记录并按证据合并；暂缓专题到 revisit_at、新增记录、未读尾批由下一全新 session 接续；开发交付唤醒原 session，测试、返工与验收闭环前不换守墓人。
- **次数是经范围复核 accepted 的独立发生事件数**。同任务重试、引用或转述不重复计数；次数仅作频率参考，不作为调查、开发或结案门槛。
- 用 `notebook.py search "组件 错误特征"` 查全历史候选（包括已审核和归档）；相关条目再 show 回读，不只比较当前批次。
- 先核验失败环节，用 group 建立单次或同源专题。cause 区分事实、假设与待验证项；根因未明时按组件/触发条件建立调查专题，不按泛化错误词合并。归属不明但确有共享流程异常时本轮调研补证，不能只因尚未定位而 excluded。
- 每个未解决专题执行 `notebook.py triage T-ID`，stdin JSON 包含 priority、decision、note、next_step；暂缓还需 revisit_at（未来 ISO8601 带时区）。note 说明影响范围、关键流程阻碍、绕行成本和证据可信度，不按次数机械定级。

| 优先级 | 判断与动作 |
| --- | --- |
| P0 | 大范围不可用、身份串用/隔离破坏、数据损坏等严重影响；decision=investigate，本轮立即启动调查和必要止损，代码修复交独立开发 |
| P1 | 已授权核心任务无法完成、身份/登录识别异常、静默失败或错误回执且缺少可靠绕行；decision=investigate，本轮启动定位修复，单个成员首次失败也适用 |
| P2 | 局部受影响、有可靠绕行但增加明显人工成本；可 investigate，或 defer 并明确下一步及复查时间 |
| P3 | 轻微问题、非关键体验改进；可 defer 留档观察，必须明确复查时间；新增证据可升级 |

```json
{"priority":"P1","decision":"investigate","note":"已授权关键流程失败、无可靠绕行；根因仍待定位","next_step":"核实身份到登录态的映射和错误处理，定位后修复并回归同类任务"}
```

- P0/P1 不能只改优先级就结束：本轮必须实际开始调查，必要时 develop 发起定位与修复，记录任务 ID 或调查证据。外部依赖导致暂时无法修复时记录具体阻塞和恢复条件，不能虚报修复。P2/P3 不因累计多次自动开发；影响变化时重新 triage。忙碌的守墓人不被强行打断，调度保留现有60秒检查和5分钟冷却。
- 流程/知识问题更新已有 SOP；需要定位或修复的程序问题启动新的 Herdr 独立开发 Agent。专题已有开发任务则复用，禁止同专题并发重复开发。
- 独立执行者从 `.codex/gravekeeper/config.json` 取配置：开发 high、纯执行 medium，显式 `-s danger-full-access -a never`；不得遗漏参数退回 Ask for approval。守墓人保持 xhigh，不直接开发。
- 开发 Agent 在 `.codex/gravekeeper/work/D-ID/` 副本记录目标路径、原文件哈希并修改候选代码，不编写/执行测试、不验收、不部署。原守墓人亲自测试；测试通过、目标基线未变、相关业务空闲才按任务授权备份并应用精确目标，守墓人执行部署验证和必要回滚。不能修改凭据、全局配置或自行扩大业务范围。涉及在线桥接，必须检查队列空闲，应用后检查服务心跳和回归结果；失败恢复备份并记录。
- 先确认工作区是否是 Git 仓库，再决定是否使用 worktree。严禁覆盖其他 Agent 的未完成修改；基线变化时重新比较并验证。
- 开发交付通过 job-ready 唤醒原守墓人。守墓人用 job-test 登记计划与候选路径并冻结哈希，亲自编写/执行测试，以 test-ready 提交实际报告；通过后仍须由守墓人 resolve 最终验收。失败则 job-reopen 交回原开发，新的开发轮次必须重新测试；开发 Agent 不能代交测试或验收。具体命令见守墓人职责。根因、关联记录、产物、验收结果均留专题，不复制到项目指令。

### 3）归档与恢复

- **每轮会话。** 先确认所有开发任务均 verified、绑定巡检已 finish、finish 之后的 Codex task_complete 已落盘且终端 idle/done，再按准确 UUID 执行 `codex archive`；回读归档标记和历史文件后关闭本轮 Herdr 标签页、移除终端。只归档会话，不删除历史。归档失败保留活动轮次并单独重试，不重做巡检；回执存 `.codex/gravekeeper/sessions/G-ID/cycle.json`。开发中、待测、测试失败、待验收或返工均阻止 finish 和归档，idle 只表示待命。仍有未验收任务的守墓人意外退出时保留原 session 归属并报告 needs_attention，先核实恢复原 session；无遗留开发任务的中断巡检才可 interrupted 归档并接续，不伪造完成。

- 每日首次调度检查：状态 verified 且关闭与最后变动均超过30天才归档；未解决事项不归档。
- 详细 JSON 压缩为 `错题本/归档/YYYY-MM/T-ID/E-ID.json.gz`，回读与 SHA256 一致后将数据库原文置空，保留事件唯一键、标题、关联专题和归档地址。原记录链接保留为可回读入口，不删除审计证据。
- 主索引最多100个活动专题和20条最近未归类记录；完整目录供人工查询，不每次交给模型。长期未解决记录保留，守墓人应明确下一步或外部依赖。
- `python3 .codex/gravekeeper/notebook.py show E-ID` 可读取并校验原文。旧问题复发用新事件 ID，并归入原 signature 重开专题。
- 归档减少活动信息和数据库大字段，不是永久清除；冷归档仍会缓慢增量，当前不自动永久删除。需要硬盘保留期限时另行确定清理规则。

## 4. 验收

- 隔离成员可读本文、可写本人 `.notebook-outbox`；共享账本、治理配置和其他成员目录仍不可访问。成员仅核对本人报告及回执，以下治理验收由获授权执行者完成。
- 无 scope 或非体系类别提交被拒且不增加记录；candidate/excluded 不能 group，只有 accepted 能建专题并评优先级；历史误收项移出活动索引但仍可回读，新证据可恢复原记录。
- 重复提交返回原 ID；同事件重试不会增加独立事件次数；并发提交不丢记录。
- Herdr agents 列表可见带 G-ID 的独立「守墓人」，每轮 session UUID 不同，实际 effort 为 xhigh；空账本不启动，工作中不重复派发。待命不归档、交付唤醒同一 UUID；全部任务通过守墓人测试并明确验收后 cycle.json 记录 session_archived=true、terminal_removed=true，归档历史仍可读。
- Hi 原 session 接收更新后的自动记录例外；本地回扫任务按原请求人/原群绑定执行，不向群广播私人历史。
- 单次 P1 经 triage 即可治理；多次但未评估或 defer 的专题不能自动开发，SOP/代码有实际产物和验收证据；启动任务不等于完成。
- 归档校验失败停止压缩状态迁移；测试在独立夹具中模拟时间，不伪造生产记录。

## 5. 异常处理

| 情况 | 处理 |
| --- | --- |
| 提交被拒绝 | 先检查是否属于体系问题；无可核验失败事实就留业务目录；已核验共享失败但根因未明可 candidate，不为通过校验编造 scope。确属体系问题再纠正格式/脱敏，不制造新 incident_key |
| Markdown 与状态不一致 | `错题本/.state/state.sqlite3` 为准，运行 `notebook.py render` 重建；不要手改生成文件 |
| 守墓人忙或审批阻塞 | 调度保留待办；在对应 Herdr 标签页查看，不强制批准或重复新建 |
| 守墓人终端退出 | 核对 last-dispatch.json、guardian_cycle、cycle.json 和未验收 jobs；有遗留任务时保留原会话并恢复，不归档或换人；无遗留任务才按 interrupted 接续 |
| 会话归档失败或缺少 finish | 归档失败仅补归档；巡检未 finish 则保留本轮并报告 attention，不当作已完成、不启动并发守墓人 |
| 调度漏发/回执不确定 | 检查 runs、revision/reviewed、hc get 和审计；begin/finish 幂等边界使未完成工作保留，别清空数据库 |
| 开发或测试失败、基线变化 | 原守墓人记录具体失败、测试证据和必要回滚，job-reopen 退回原开发，保留 session；开发只修代码，守墓人重新测试验收 |
| 归档损坏 | 保留文件与错误，使用原始备份恢复，不把损坏记录标为已验证 |
