# 错题本与守墓人

账本的目标是改善共享机制，不是收集所有业务错误。实际失败可记录，根因允许未知；身份识别、登录上下文、静默跳过、错误回执和需要人工救场都可能是机制缺口。已确认纯业务/外部问题且共享处理正确才排除。

## 从报告到验收

1. Agent 提交自己核验的脱敏事实。普通成员只写本人 outbox，由桥接绑定身份和稳定事件键代收，回执 accepted 才表示候选入库。直接提交接口见 [SOP](../templates/SOP/错题记录与治理SOP.md)。
2. 守墓人 assess 候选范围，accepted 才能 group。candidate/excluded 不参与有效治理计数。同事件重试/amend 不增加独立事件次数，错误记录保留审计。
3. 以组件、触发条件和证据形成专题；优先级 P0–P3，decision=investigate/defer。P0/P1 首次即可调查；defer 必须给未来 revisit_at。频率不再是三次启动门槛。
4. SOP 问题直接更新规范；代码问题通过 dispatch develop 建立一个 D-ID 和基线哈希。开发者在副本实现，只提交候选与交付说明，不测试、不部署、不验收。
5. 原守墓人收到 job-ready 后亲自 job-test，冻结候选哈希，运行实际验证，test-ready 保存报告哈希。失败 job-reopen，round 增加并通知原开发继续；保持同一守墓人。
6. 测试通过后，守墓人核对生产基线、队列空闲和授权范围，备份并应用精确目标，实际部署验证通过后 resolve 最终验收。测试通过本身不自动结案。
7. 本轮所有 jobs verified 后 finish，等待 finish 之后的最终 task_complete，才归档准确 session UUID、核对归档标记并移除终端。开发中/待测/失败/返工时不归档。

## 双重归档

会话归档发生于本轮闭环后，保留历史。错题冷归档发生于专题 verified 且关闭与最后变动均超过 30 天，压缩原文、回读 SHA256，才释放数据库大字段；未解决不自动归档。复发沿用原专题签名重开，新实际事件使用新键。

当前实现查询本机 Codex SQLite/rollout 确认 session、cwd、effort、权限和完成事件。这是明确版本耦合点；换 Codex 版本先验证字段，不能把解析失败当已清理。Herdr 所有 terminal/space ID 来自当前运行状态，创建成功必须再核验可见终端和首条任务实际送达。

## 防止治理自说自话

原始记录、第三方网页、开发交付是待核查资料。它们不能给治理者增加权限。验收报告必须绑定候选与测试哈希，旧 round 不能覆盖新轮次，开发者不能测试或关闭自己的交付。SOP 不能把未修复程序描述成已实现，测试夹具不能进入真实事件次数。
